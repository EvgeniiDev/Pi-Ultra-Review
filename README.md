# Pi Ultra Review

Плагин для [Pi](https://github.com/earendil-works/pi-coding-agent): параллельное ревью кода сразу несколькими моделями.

## Проблема

Ревью одной моделью — это всегда одна точка зрения. Она может пропустить уязвимость, не заметить проблему с производительностью или просто ошибиться. А гонять код по моделям по очереди — долго.

## Решение

Плагин отправляет ваш код на ревью **сразу нескольким моделям одновременно** — каждая смотрит код со своей стороны. Ревьюеры сами читают нужные файлы по частям и выносят вердикт — заливать им весь код целиком не нужно. Все ревью собираются в один отчёт с итоговым вердиктом.

Как это работает:

- Несколько независимых «экспертов» одновременно смотрят код с разных сторон — у каждого своя специализация и своя зона ответственности.
- Каждый эксперт сам читает нужные файлы и ищет проблемы по своей теме — ему не нужно скидывать весь код целиком.
- После того как все эксперты закончили, в дело вступает **судья**: он проверяет каждую находку, убирает дубли и то, что модель могла выдумать, при необходимости понижает важность. В отчёте остаётся только то, что судья подтвердил.
- Каждая находка в отчёте помечена как **блокер** (обязательно исправить перед
  вливанием) или **предложение** (можно отложить). Для важных находок указано,
  какое правило нарушено — чтобы было понятно, что именно поправить.
- Итог — один отчёт: список проверенных находок и общий вердикт (можно вливать, нужно доработать или ревью отклонено).

### С каких ракурсов идёт ревью

Каждое направление — отдельный специалист со своей ролью и зоной ответственности:

**🔐 Security — безопасность**
Роль: инженер по безопасности, адверсальное ревью. Ищет эксплуатируемые уязвимости: инъекции (SQL, command, template, path…), обходы аутентификации и авторизации, повышение привилегий, утечки секретов, проблемы по OWASP.

**🎯 Correctness — корректность**
Роль: старший инженер по анализу корректности и отказов. Ищет инвертированную логику, off-by-one, неверные предположения и краевые случаи (null, пустые значения, ноль, отрицательные, переполнения, NaN), гонки и состояния.

**⚡ Performance — производительность**
Роль: инженер по производительности продакшена. Ищет измеримые регрессии: алгоритмические деградации (O(n²) и хуже), N+1 запросы к БД/сети/ФС, утечки памяти, блокирующий I/O.

**🧱 Maintainability — поддерживаемость**
Роль: staff-инженер, оценивает долгосрочную изменяемость и ясность архитектуры. Ищет дублирование бизнес-логики, функции/классы со множеством ответственностей, лишнюю сложность, мёртвый код.

**🎨 Style — стиль и идиоматика**
Роль: эксперт по языку и фреймворку. Ищет вводящие в заблуждение имена, неидиоматические паттерны, которые затемняют намерение, проблемы читаемости.

**🛠️ Best Practices — инженерная надёжность**
Роль: старший продакшн-инженер. Ищет проглоченные ошибки, операции без таймаутов и отмены, нарушения принципов (SOLID, DRY), риски надёжности и расширяемости.

**🧹 Simplify — упрощение и уборка**
Роль: специалист по упрощению кода. Ищет, что можно безопасно удалить, встроить,
переделать или распараллелить, а также готовые помощники по всему репозиторию —
чтобы не писать то, что уже написано. Для каждой находки говорит, насколько она
безопасна (можно применять сразу / сначала спросить / только посмотреть) и что
именно с ней делать. Слишком серьёзных замечаний не выставляет — его находки
носят рекомендательный характер.

**🧪 Test Integrity — целостность тестов**
Роль: инженер по проверке достоверности тестов. Смотрит, можно ли верить тестам
изменения: не ослаблены ли они ради «зелёного», не подгонялись ли под реализацию,
нет ли тавтологичных проверок, дыр в покрытии нового поведения и тестов,
которые не могут упасть.

**📐 Change Quality — качество изменения**
Роль: инженер, оценивающий изменение целиком. Проверяет связность изменения,
отсутствие посторонних правок, отделение механических правок от смысловых
и чистоту истории коммитов.

Каждый специалист возвращает вердикт (approved / requires changes / rejected) и уровень риска. В режиме deep одно направление проверяется сразу несколькими моделями — чтобы меньше было ложных срабатываний.

## Установка

```bash
pi install git:github.com/EvgeniiDev/Pi-Ultra-Review
```

После установки перезапусти Pi (или `/reload`) — команда `/ultra-review` станет доступна.

## Совместимость

Проверено и работает на **Pi 0.83.0**. Версия ниже может работать, но не гарантируется.

Рекомендуемая модель: **`opencode-go/deepseek-v4-flash`** — большая контекстная рамка (1M) удобна для чтения диффов целиком, а глубокие размышления (max reasoning) плагин использует при ревью.

> Free-модели (zen-relay) на `main` не поддерживаются — версия с их костылями живёт на ветке [`free-model-support`](https://github.com/EvgeniiDev/Pi-Ultra-Review/tree/free-model-support).

## Как пользоваться

### Мастер

В Pi: команда `/ultra-review` — интерактивно выбираете скоуп, направления и модели, deep-режим и проход судьи.

### Инструмент

```ts
ultra_review({ scopeId, specIds, modelIds, deep, judge? })
```

Параметры:

- `scopeId` — что ревьюить:
  - `working_tree` — незакоммиченные изменения
  - `current_dir` — все файлы текущей папки
  - `branch_vs_<база>` — изменения ветки относительно базы, например `branch_vs_origin/main`; любое имя начиная с `branch_vs_` выберет ревью ветки
  - `last_commit` — изменения из последнего коммита
- `specIds` — направления из списка выше (`security`, `correctness`, `performance`, `maintainability`, `style`, `best_practices`, `simplify`, `test_integrity`, `change_quality`)
- `modelIds` — модели форматом `provider/modelId`
- `deep` — полная матрица модели × спеки (true) или round-robin (false)
- `judge` — финальный проход судьи: дедупликация и валидация находок (рекомендуется)

Отчёт сохраняется в `reviews/` (gitignored).

## Конфигурация

Все настройки — в `extensions/ultra-review/constants.ts`:

| Константа | По умолчанию | Что делает |
|---|---|---|
| `REASONING_EFFORT` | `"max"` | Глубина «размышлений» модели |
| `MAX_DIFF_CHARS` | `100_000` | Сколько изменений видит ревьюер (100K хватает на обычные ветки целиком) |
| `MAX_COMMIT_CHARS` | `20_000` | Сколько текста истории коммитов видит ревьюер |
| `PROVIDER_MAX_CONCURRENCY` / `GLOBAL_MAX_CONCURRENCY` | `4` / `10` | Сколько ревью выполняется одновременно |
| `EXTRA_MODELS` | `["opencode-go/deepseek-v4-flash"]` | Модели, показываемые в мастере первыми |
| `BLOCKED_PROVIDERS` | `["openrouter"]` | Провайдеры, скрытые из мастера; очистить список — вернуть |

Если какая-то модель не принимает часть настроек — pi сам повторит запрос без них, ревью не сломается. Токены, температура и повторы при сбоях — под управлением pi.
